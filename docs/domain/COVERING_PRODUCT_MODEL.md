Manufacturer data can change. Before a catalogue revision is published, each value must be rechecked against the current technical sheet and stored under a new `technicalRevisionId`.

## V18 conclusions

- The supported technical families are discriminated as `roof-tile`, `modular-sheet`, and `standing-seam`.
- Physical size, effective/covering size, gauge, installation mode, pitch limit, and panel-length model are distinct concepts.
- A project stores an immutable technical snapshot. An optional catalogue reference identifies where it came from; it does not replace the snapshot.
- Technical schemas contain no price, currency, supplier SKU, stock, or discount fields.
- Compatibility is a structured result. Missing mode or batten gauge is reported explicitly and never silently defaulted.
- V18 defines strategy inputs and outputs but intentionally does not calculate covering quantities. Tile, sheet, and seam layout algorithms belong to V19/V20.

## Quantity bridge

Future covering engines receive neutral roof-plane geometry, canonical openings, and the selected technical snapshot. Their results can implement a covering quantity source consumed by `quantity-core`. `quantity-core` remains the aggregation boundary; `roof-math` must not import product, catalogue, price, or commercial data.
