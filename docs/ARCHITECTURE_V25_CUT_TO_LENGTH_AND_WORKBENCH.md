# Architecture V25 — Covering workbench and cut-to-length metal

Status: source implementation and targeted automated validation in Iteration 025. Physical browser/mobile acceptance remains unavailable in this session.

## Product and calculation path

The Covering centre owns product/source identity, whole-assignment result, selected-plane result, polygon drawing and quantity boundary. The Inspector owns exact product, width/length, layout and plane-assignment edits in Product, Installation, Covering Dimensions and Layout sections, with advanced physical values collapsed. Catalogue/manual selection both store a technical snapshot; the same resolver sees only the snapshot, layout intent and neutral plane/opening geometry. A catalogue `modular-sheet` product with `lengthModel.kind: cut-to-length` selects the new resolver automatically. A manual metal assignment can choose fixed size or cut to length using human-facing format labels. The picker filters by covering family, shows the metal format/length range, and pages beyond its first 30 results; users do not choose a solver class. On mobile, opening the picker closes an Inspector sheet so only one sheet owns the screen. Fixed modular sheets remain on their V21 resolver, tiles on V19 and standing seam on V22. The older direct Add Covering actions remain visible in V25; a single category-first add flow is deferred to avoid disrupting the established creation path without live interaction QA.

`CoveringLayoutIntent` adds `modular-sheet-cut-to-length` with centred/from-U-min/manual alignment and optional plane offsets in canonical millimetres. Existing fixed-sheet intents remain valid. Older cut-to-length snapshots with a V21 `modular-sheet` intent parse and are adapted when resolving; applying a new catalogue product writes the dedicated intent. One normal assignment edit feeds V23 dirty/autosave. Drawing-detail Auto/Detailed/Simplified is component view state and creates no technical edit or history entry.

## Pure variable-panel adapter

`resolveCutToLengthSheetLayout` reuses V22 `resolveVariablePanelPlane` without copying polygon clipping, coherent U-grid placement, opening subtraction or connected-component logic. It matches only explicitly supplied opaque plane IDs. The grid step is `effectiveWidthMm`; `totalWidthMm` is reference-only. Each connected visible component becomes one geometric physical run, with stable assignment/plane/column/run identity, from/to V, geometric length, width classification and issues. Full-width openings create separate lower and upper runs. Hip triangular and trapezoidal polygons use the same kernel.

`CutToLengthSheetLayoutResult` reports assignment status, per-plane and total strip/run counts, full-width and edge-cut strips, opening-interrupted runs, total geometric length, min/max run lengths and exact length groups. A hip strip with a diagonal roof edge counts as edge-cut even when its nominal eave width is full; this classification uses the already clipped kernel polygons. `geometricLengthMm` is the longest V extent of a connected visible component. `orderLengthMm` is deliberately absent: the existing module field does not encode the product-specific starting offset, end allowance or permitted manufactured lengths. No rounding or module-step guess enters quantity. A run above the technical maximum reports `segmentation-required` and remains one candidate. No transverse joint location, overlap, batten support or water-flow detail is generated; a too-short run reports its minimum violation. Pitch below the snapshot minimum blocks trusted quantity. A limited result may still show geometric quantity with explicit issues; it is never a purchase list.

`createCutToLengthSheetQuantitySource` emits run count in pieces, aggregate geometric length and exact mm length groups through the established covering quantity bridge. The material schedule starts compact and discloses groups on request. Its wording distinguishes geometric runs from amounts to buy; waste, offcuts, accessories, price and fabrication orders are excluded. One-primary-covering-per-plane ownership filtering is applied before all family solvers.

## Catalogue and schema boundary

The V24 SQL schema remains unchanged: technical revisions hold validated JSON. The DEMO-only cut-350 family/revision/variant in the canonical fixture proves import, read API, exact revision, snapshot, solver and quantity. Revision code is copied into a small display snapshot so source identity can be shown without exposing a raw technical ID. The immutable revision ID remains the calculation provenance; same-ID changed technical data conflicts, while a new ID is accepted. If a user edits a catalogue-derived technical value, the assignment detaches its catalogue reference and revision label in that same project edit, so a modified manual snapshot cannot falsely claim an exact technical revision. Reopening a stored assignment resolves from its snapshot when the API is unavailable.

## View and performance boundary

The workspace renders detailed polygons for ordinary layouts and simplified technical lines above the existing 1200-fragment threshold. The Auto/Detailed/Simplified control changes rendering only. The domain result and quantity do not depend on it. Layout resolution is memoized in `Page` on canonical inputs; picker search and viewport controls are outside those dependencies. Opening polygons, plane outline, selected-plane tabs, result scope and Inspector access remain visible on desktop and mobile. Live CSS/viewport and physical touch checks are still required when the in-app Browser is available.
